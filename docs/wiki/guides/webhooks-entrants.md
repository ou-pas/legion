# Connecting forge webhooks

Once connected, GitHub and GitLab tell Legion when a change request is merged, and the task in review
that carried it moves to done without you going there. The concept is described in
[[concepts/forge]]; this page is the how-to, in three moves.

## 1. Expose the /webhooks path with Tailscale Funnel

The control plane lives on the tailnet, which forges cannot reach. Tailscale Funnel exposes one
specific path of the machine on a public https URL, without opening a port on your side. On the
control plane machine:

```
sudo tailscale funnel --bg --set-path=/webhooks http://127.0.0.1:8790/webhooks
```

`tailscale funnel status` shows the public URL obtained, of the form
`https://<machine>.<tailnet>.ts.net`. Only the `/webhooks` path is served publicly: the operator
session guard does not apply to this prefix, each request's signature decides, and the server reserves
the prefix so that nothing else, the UI included, is ever served on it. Never mount the root.

## 2. Set the public URL

In System → General, Inbound webhooks card: paste the funnel's public URL, without a path. The secret
that will sign the requests is generated by the server on the first connection; it is presented to the
forges through their API and shown nowhere. Creating the secret requires the master key
(`LEGION_MASTER_KEY`): an instance without it will not write to disk, in clear, a secret that also
lives at the forge.

## 3. Connect each repo

In the project's Settings → Repos, each row carries a Connect the webhook button. It creates the hook
through the forge's API with the token already among the project's secrets (`GITHUB_TOKEN` with the
right to administer the repo's hooks, `GITLAB_TOKEN` with the `api` scope), subscribed to change
request events only. The chip turns to "webhook connected".

If the public URL changes later, the chip says the webhook needs reconnecting: the forge's hook calls
the old address. Reconnecting creates one on the new address; the old one is deleted in the repo's
settings, on the forge side.

## Checking it works

Merge a change request carried by a task in review: the task moves to done within a minute of the
click, and the task's trace carries the reason. On the forge side, the hook page lists each delivery
with Legion's response. A 200 with `matched: 0` means "nobody was following this PR", which is the case
for every human PR, and a 503 means "I could not verify, deliver again" (GitLab retries on its own,
GitHub has a Redeliver button).
